# CV Operator Workflow Refactor

This document is scoped by `docs/architecture/cv-platform-spec.md` and keeps its non-negotiable service boundaries intact:

- admin API remains the orchestration authority
- realtime and batch inference stay separated behind distinct gateways
- training, packaging, deployment, and serving remain distinct internal stages
- no operator CLI is introduced for the normal workflow

## Current-State Problem

The existing admin web app behaves like a platform control panel instead of an operator workflow. The normal user is pushed through separate areas for:

- project mapping
- snapshots
- training
- models and registry
- deployments
- realtime testing
- batch
- audit and settings

That fragmentation causes three operator-facing problems:

1. The happy path requires hopping across multiple pages for one business outcome.
2. Several pages expose technical identifiers and low-level lifecycle steps too early.
3. The Label Studio-first workflow is not fully real when assets originate in Label Studio instead of the platform upload flow.

## Hidden Assumptions

These assumptions mattered during the refactor:

- Label Studio project discovery must be automatic by webhook and scheduled sync, but manual reconciliation still needs to exist as a fallback.
- A discovered Label Studio project can own a platform dataset automatically without collapsing the dataset architecture.
- Operators should create a model once with minimal inputs; internal slugs, IDs, and endpoint names should be generated from project and preset context.
- Auto-deploy can be on by default only when quality gates pass and the currently healthy deployment stays untouched on failure.
- Public endpoint visibility must stay separate from admin orchestration, so endpoint detail pages can read from inference gateways without merging those service boundaries.
- Snapshot automation has to work even when images were uploaded directly into Label Studio, not just through platform upload sessions.

## Chosen Safer Option

Where assumptions mattered, the implementation chose the more operator-friendly and production-safe option:

- Auto-create a dataset for newly discovered Label Studio projects instead of forcing manual mapping for the happy path.
- Keep manual project mapping as an advanced fallback under Operations.
- Default project automation to `auto_sync_enabled=true`, `auto_snapshot_enabled=true`, `auto_train_enabled=false`, and `auto_deploy_enabled=true`.
- Train from the latest valid snapshot by default, but keep advanced overrides behind explicit controls.
- Package after successful training automatically, then auto-deploy only if promotion gates pass.
- Preserve the previously healthy release when training or deployment fails.
- Cache missing Label Studio-managed assets into the platform dataset asset store during snapshot materialization so the Label Studio-first workflow is real.

## Updated UX Specification

### Main Navigation

Primary navigation now prioritizes:

- `Overview`
- `Projects / Pipelines`
- `Models`
- `Inference Endpoints`
- `Operations / Advanced`

### Primary Object: Project Pipeline

Each Label Studio project is represented as one pipeline-centric workspace showing:

- Label Studio sync state
- annotation readiness
- latest dataset and latest valid dataset
- model presets and created models
- training history and active run state
- current deployment and endpoint availability
- activity timeline
- recommended next action

### Happy Path

The intended operator flow is now:

1. Annotate in Label Studio.
2. Open `Projects / Pipelines`.
3. See the discovered project and latest valid dataset automatically.
4. Create a model with a small preset form.
5. Start training from the pipeline page.
6. Watch progress and quality gate state on the same page.
7. Open the resulting endpoint detail once packaging and deployment complete automatically or after one approval action.

### Advanced Mode

Low-level pages remain available under `Operations / Advanced`:

- manual project mapping
- snapshot internals
- validation details
- registry internals
- deployment control
- advanced realtime test console
- advanced batch tooling
- audit
- settings
- health

## Naming Conventions

The happy path now uses generated names:

- Dataset snapshots: immutable internal ids remain autogenerated; operator labels use `Snapshot {snapshot_no}`.
- Model display names: default to `{Label Studio project title} Detector` or `{Label Studio project title} Classifier`.
- Internal model slugs: `slugify(display_name)`.
- Public endpoint names: same as model family slug for a stable operator-visible logical name.
- Deployment releases: immutable internal ids remain backend-managed and hidden from the normal flow.

Example:

- Label Studio project: `Cars Inspection`
- Default model display name: `Cars Inspection Detector`
- Generated slug: `cars-inspection-detector`
- Public endpoint name: `cars-inspection-detector`

## Implementation Notes

### Backend

- Label Studio project discovery now auto-creates a platform dataset when needed.
- Project automation policy fields were added to `label_projects`.
- Project-owned model family metadata was added to `model_families`.
- Pipeline aggregation helpers now produce project-centric summaries and details.
- Post-training automation now packages automatically and deploys according to project policy.
- Snapshot materialization now caches missing Label Studio-owned assets into the dataset asset store when they were never uploaded through the platform upload flow.

### Frontend

- The router and sidebar were refactored around the project-centric workflow.
- New pipeline list and pipeline detail views anchor the operator happy path.
- Top-level `Models` and `Inference Endpoints` are now operator-friendly summary views.
- `Operations / Advanced` collects low-level admin pages instead of leaving them in the main path.
- Endpoint detail pages now show application-facing contract information and a quick realtime test action.

## Migration Notes

- Operators should use `Projects / Pipelines` instead of `Projects`, `Snapshots`, `Training Jobs`, `Experiments & Registry`, and `Deployment` for the normal flow.
- Engineers can still access the previous detailed pages under `Operations / Advanced`.
- Saved links to legacy top-level pages continue to work through redirects.
- Saved links to legacy snapshot detail pages continue to render directly.
- The project mapping page is no longer required for normal operations, but it remains available for migrations and edge cases.
